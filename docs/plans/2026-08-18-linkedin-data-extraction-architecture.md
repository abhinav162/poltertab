# Architectural Plan: Advanced Data Extraction for Obfuscated SPAs (LinkedIn)

## 1. Problem Statement

Extracting data from modern SPAs like LinkedIn via traditional DOM scraping is unreliable due to:

- **Obfuscation**: Autogenerated, non-semantic CSS class names (`.sc-1a2b3c`, etc.).
- **Virtualization**: Elements off-screen are removed from the DOM (e.g., `react-window`), breaking `.innerText` dumps.
- **Lazy Loading**: Data is only fetched when scrolled into view.

## 2. Research & Evaluation of Network Interception Methods

To bypass the DOM entirely, we must capture the raw JSON data (GraphQL/XHR) driving the UI.

### Option A: `chrome.debugger` API (CDP)

- **Pros**: Access to `Network.getResponseBody` without touching the page context. Can trigger CDP scroll events.
- **Cons**: Shows a persistent "ZeroClaw Browser Control started debugging this browser" warning bar at the top of the browser. Destroys UX.
- **Verdict**: Only suitable for headless/automated testing, not for seamless agent-assisted browsing.

### Option B: `chrome.declarativeNetRequest`

- **Pros**: Native MV3 API. Invisible to the user.
- **Cons**: Only supports blocking, allowing, modifying headers, or redirecting. It **cannot read response bodies**.
- **Verdict**: Unusable for data extraction.

### Option C: Service Worker `fetch` Listeners

- **Pros**: Standard Service Worker feature.
- **Cons**: In MV3 extensions, the background service worker only intercepts the extension's *own* network requests, not the requests made by the tabs.
- **Verdict**: Unusable for tab data extraction.

### Option D: Main World Script Injection (Monkey-Patching)

- **Pros**: Completely invisible to the user. Direct access to response bodies.
- **Cons**: Requires injecting a script into the `MAIN` execution world of the page (not the `ISOLATED` world where standard content scripts live).
- **Mechanism**: The injected script overrides `window.fetch` and `XMLHttpRequest.prototype.open/send` to capture GraphQL responses, then uses `window.postMessage` to pass the JSON to the isolated content script, which forwards it to the background script.
- **Verdict**: **The optimal solution** for seamless, invisible data extraction.

## 3. Proposed Architecture

### Bypassing Virtualization (In-Memory Data Store)

Instead of scraping the DOM, the extension will build an **In-Memory Network State Map**.

1. As the user or agent navigates, the Main World Script intercepts `/graphql` or `/api` responses.
2. The JSON payloads are parsed and normalized (e.g., extracting `comments`, `posts`, `profiles`).
3. This state is stored in the `background.js` or MCP server.
4. When the agent requests `browser_get_network_state`, the MCP server queries the in-memory JSON state rather than the DOM, completely bypassing virtualization constraints.

### Handling Lazy Loading

To fetch data that hasn't loaded yet without manual scrolling, the agent can use two methods:

1. **Synthesized Scrolling**: Send a command to the content script to execute `window.scrollBy(0, 1000)`. Wait for the intercepted network requests to populate the State Map.
2. **Replaying Requests (Advanced)**: The Main World Script captures the authentication headers (`csrf-token`, Bearer tokens) from the intercepted requests. The extension can then securely replay the GraphQL requests in the background to fetch the next pages (pagination) instantly, without touching the UI.

## 4. Data Flow Diagram

```text
[ LinkedIn Tab ]
      │
      ├─► (1) User/Agent triggers navigation or scroll
      │
      ├─► [ MAIN World Script (Injected) ]
      │     - Overrides window.fetch & XHR
      │     - Captures GraphQL JSON responses
      │     - window.postMessage({ type: 'ZC_NETWORK_DATA', data: ... })
      │
      ▼
[ ISOLATED World Content Script ]
      │     - Listens for 'message' events
      │     - chrome.runtime.sendMessage({ type: 'ZC_NETWORK_DATA', ... })
      │
      ▼
[ background.js (Service Worker) ]
      │     - Forwards via WebSocket to MCP Server
      │
      ▼
[ Node.js MCP Server ]
      │     - Updates In-Memory Network State Map
      │     - Resolves agent queries against structured JSON (not DOM)
      │
      ▼
[ AI Agent (Claude/ZeroClaw) ]
```

## 5. Actionable Implementation Steps for ZeroClaw

### Step 1: Create the Interceptor Script

Create `chrome-extension/interceptor.js`. This script will monkey-patch `fetch` and `XHR`.

```javascript
// interceptor.js
const originalFetch = window.fetch;
window.fetch = async (...args) => {
  const response = await originalFetch(...args);
  const clone = response.clone();
  clone.text().then(body => {
    if (args[0].includes('graphql') || args[0].includes('api')) {
      window.postMessage({ type: 'ZC_NETWORK_DATA', url: args[0], body }, '*');
    }
  }).catch(() => {});
  return response;
};
// Add similar logic for XMLHttpRequest
```

### Step 2: Inject the Script via Content Script

Update `content_script.js` to inject `interceptor.js` into the `MAIN` world at `document_start`.

```javascript
// content_script.js
const script = document.createElement('script');
script.src = chrome.runtime.getURL('interceptor.js');
(document.head || document.documentElement).appendChild(script);

window.addEventListener('message', (event) => {
  if (event.data && event.data.type === 'ZC_NETWORK_DATA') {
    chrome.runtime.sendMessage(event.data);
  }
});
```

### Step 3: Update Manifest Permissions

Add `interceptor.js` to `web_accessible_resources` so it can be loaded into the page.

```json
"web_accessible_resources": [
  {
    "resources": ["interceptor.js"],
    "matches": ["<all_urls>"]
  }
]
```

### Step 4: Expose Data to the MCP Server

In `mcp-server/index.js`, track the intercepted data per tab session in a rolling buffer.
Add a new MCP tool `browser_get_network_state` that the LLM can call to retrieve the captured JSON structures (e.g., LinkedIn feed data) instead of relying on `browser_get_text`.

### Step 5: Implement Smart Scroll for Lazy Loading

Add a tool `browser_smart_scroll` which scrolls the page and waits for new `ZC_NETWORK_DATA` events to arrive via WebSocket before returning success. This guarantees that lazy-loaded network data has been captured by the In-Memory Store before the agent proceeds.
